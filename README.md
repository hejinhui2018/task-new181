# ClauseHarbor · 保险产品条款审核交付台

产品法务把新版保险条款交各地区审核的工作台：维护条款、定义引用、产品与地区覆盖，按**评审轮次**查看地区意见、条款间冲突与生效准备度；退回 / 补交 / 替换产生新版本，**旧轮次、旧版本结论永不覆盖当前结论**；就绪条款组装发布包交给发布同事，未通过或缺依赖的内容留在隔离区。全部数据保存在本机浏览器，刷新、崩溃后版本关系、评审意见与发布回执仍一一对应。

## 运行

零运行时依赖（Node ≥ 18，仅用于起静态服务器和跑测试）：

```bash
node server.js          # http://127.0.0.1:8080
# 或直接用任意静态服务器指向本目录，然后打开 index.html
```

首次打开自动载入演示数据（8 条条款 / 5 个地区 / 2 轮评审 / 2 个发布包，覆盖全部典型场景）。顶栏「重置演示」可随时还原。

## 六个工作台

| 视图 | 能做什么 |
|---|---|
| **总览** | 在管条款 / 就绪 / 隔离 / 已发布 KPI，准备度分段条，责任范围冲突、替换残留、定义变更、过期发布包的告警，隔离区速览与操作留痕 |
| **条款库** | 按就绪 / 隔离 / 草稿 / 已发布筛选与全文搜索；抽屉内编辑草稿、送审、撤回、补交 / 替换、查看版本谱系与各轮意见 |
| **定义与引用** | 维护术语释义；定义更新后，「通过在先、变更在后」的地区结论自动失效需复审；已发布回执不受影响仅提示下一发布包对齐 |
| **产品与地区** | 产品上线地区、条款 × 地区审核矩阵（✓ 通过 / 退 退回 / 待 待审 / 缺 地区缺口 / · 不适用），双向关联 |
| **评审轮次** | 同时只有一个进行中轮次；每条意见绑定**条款 + 具体版本 + 地区**，旧版本意见标记「历史留痕」 |
| **发布与隔离** | 就绪条款封包（快照 + 逐条指纹 + 整包指纹），过期旧版 / 封包后依赖变更会拦下发布；已发布回执可随时重新校验；隔离区列出每条阻断原因与「去处理」入口 |

## 核心规则（全部由 `js/engine.js` 派生计算，可随时重算）

1. **结论只认「当前版本 + 最新轮次」。** 退回、补交、替换一律生成新版本并冻结旧版本；对旧版本登记意见会被拒绝。
2. **逐地区、逐定义的失效判定。** 定义在某地区「通过」时间之后更新，该地区的通过即失效（其他地区不受背书）；在定义更新后的轮次重新表态才恢复就绪。
3. **冲突检测：**
   - `definition-missing` 引用了不存在的定义；
   - `definition-changed` 定义变更后需复审；
   - `effective-inversion` 替换版生效日期早于被替换版本（生效倒挂）；
   - `coverage-conflict` 同一产品下同一责任项既保障又除外；
   - `region-gap` 产品上线地区超出条款适用地区；
   - `missing-region-approval` 当前轮次仍有地区未通过 / 未弃权；
   - `replacement-residue`（警告）进行中轮次仍在给被替换的旧版本下意见。
4. **发布包是不可变快照。** 封存后条款再改产生新版本，不影响包内快照；带旧版或已变更依赖发布将被拒绝，必须解散重组。发布后置版本为 `published`，冻结发布轮次号，生成条目指纹 + 回执指纹，刷新或导入备份后均可复验；篡改任何封存正文都会使校验失败。
5. **草稿 / 撤回：** 已送审版本不能直接覆盖；尚无意见时可撤回为草稿；有意见后只能走补交。表单草稿走独立存储通道（800 ms 自动暂存），事务崩溃不丢草稿。

## 持久化与异常恢复（`js/store.js`）

每次写操作走 WAL 三段式事务：

```
1. 写 ch.wal（整库快照 + FNV-1a 校验和）
2. 旧主库存 ch.backup
3. 主库 ch.db 切换为新状态
4. 删除 ch.wal
```

启动时按恢复链处理：WAL 与主库一致 → 仅清理 WAL；WAL 有效而主库落后 → 前滚；WAL 损坏 → 忽略未完成事务；主库损坏 → 回滚备份。每次恢复都会在工作台顶部显示一次黄色横幅说明。表单草稿键（`ch.draft.*`）不参与事务，保证「填了一半」的内容独立存活。

顶栏支持 **导出 / 导入 JSON 备份**（导入前校验校验和，不一致直接拒绝），适合发给发布同事或换机使用。

## 目录结构

```
index.html          工作台骨架
css/styles.css      浅色 / 深色两套主题（dataviz 参考色板，状态一律「色点+文字」）
js/engine.js        纯逻辑引擎：版本谱系、评审聚合、冲突、准备度、发布包/回执
js/store.js         WAL 事务、启动恢复链、表单草稿、备份导入导出、回执校验
js/seed.js          固定时间线的演示数据
js/app.js           六个视图 + 抽屉 + 动作编排（所有写操作经事务提交）
server.js           零依赖静态服务器
test/               node:test 引擎/存储测试 + jsdom 界面端到端测试
```

## 演示数据里的典型场景

- **CL-MED-02**：第1轮四川通过、湖北退回 → 补交 v2 → 第2轮四川重新通过、湖北未表态（旧退回只留历史）；其后「医疗必需」定义更新，四川也需在更新后重新表态。
- **CL-WAI-03**：v1 五通道中两地第1轮通过并已发布 → 第2轮广东补了备案意见 → 法务替换出 v2 草稿且生效日期 6 月早于 v1 的 7 月（生效倒挂）；广东旧意见显示为替换残留。
- **CL-HALF-05 vs CL-RES-06**：同一产品对「高原反应医疗」一个除外一个保障（责任冲突），且后者没覆盖产品上线的湖北（地区缺口）。
- **CL-CRI-04 / PK-002**：条款第1轮通过并封入待发布包，封存后定义更新 → 包标记「快照已过期」，发布按钮禁用。
- **CL-GEN-08 / PK-001**：已发布回执，后续任何条款变更都不影响其指纹，可反复复验。
- **CL-SPO-07**：草稿引用了不存在的定义且地区未覆盖，隔离原因一次性列全。
